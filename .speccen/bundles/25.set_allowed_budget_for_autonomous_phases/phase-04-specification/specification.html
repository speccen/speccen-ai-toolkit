A fix budget for the gate test

In an autonomous phase, the delegate corrects a failed gate test up to a number of fix attempts that the Architect sets. The delegate halts sooner when a correction would change a conclusion, or when a verifier run makes no progress.

What the update builds

At the end of an autonomous phase, the delegate writes the gate test. A verifier examines every row. Today the delegate gets one fix attempt. If an examined row still fails, the delegate halts, and the Architect must reply.

Most of these stops are about small faults: a line number, a total, a quote. The Architect almost always replies "yes". The stop adds no decision.

This update adds a key to the project file, fixes. The key sets how many fix attempts the delegate makes before it halts: 1 to 10. The default is 5; set fixes: 1 to keep one fix attempt. Three guards keep the loop safe:

  • Conclusions. If the next correction would change a phase conclusion, a delegated decision or an ADR, the delegate halts immediately.
  • Progress. If a breach from the previous verifier run comes back, or more rows fail, the delegate halts.
  • Ceiling. The delegate makes at most 10 fix attempts.

Source: the Architect's brief (issue #25), the Phase 01 analysis and the Phase 03 decisions.

The gate test (L3)

The guards, in order:

  1. Conclusions — the next correction changes a phase conclusion, a delegated decision or an ADR: a stop, in every phase.
  2. Budget — an examined row still fails and the delegate used all its fix attempts: a stop. The Phase 05 accept step rejects the implementation instead.
  3. Progress — a breach from the previous verifier run is still there, or more rows fail than in the previous verifier run: a stop. The Phase 05 accept step rejects the implementation instead.

After a stop, the Architect's answer sets the rows for the next verifier run, and whether the delegate may make more fix attempts. Without such an answer, one verifier run follows, and a failed row is a new stop.

The key (L3)

  • Top level: fixes, a whole number from 1 to 10. Phase level: phases.<phase>.fixes, also inherit.
  • Phases: the five phases that have a stops key, from Feature Analysis to Implementation.
  • Resolution: the most specific setting wins, as for stops. The default is 5.
  • Fail-safe: a value that is not a whole number from 1 to 10 counts as 1.
  • Locks: a project lock prevents a higher fixes in a bundle file or a local file.
  • Upgrade: a version-2 project file gets fixes: 5, fixes: inherit on five phases and version: 3. No value the Architect set changes.

Requirements and acceptance scenarios

R-1 — The key

The project file SHALL have a fixes key at the top level and on the five phases that have a stops key. Its values SHALL be the whole numbers 1 to 10, and also inherit at phase level. The key SHALL have an effect only in autonomous phases. It SHALL be independent of stops.

  • WHEN a project file sets phases.code-analysis.fixes: 2 and the phase is autonomous
  • THEN the gate test of that phase allows two fix attempts.
  • WHEN the phase is gated
  • THEN fixes has no effect.

R-2 — Default 5

The default SHALL be 5.

  • WHEN no file sets fixes
  • THEN the gate test allows up to five fix attempts, then a stop.

R-3 — The fix loop

The delegate SHALL correct a failed gate test and repeat the verifier run, up to the effective fixes attempts. Each later verifier run SHALL examine the rows that failed in the previous run and the rows that cite a changed file.

  • WHEN fixes: 3 and run 1 fails two rows
  • THEN the delegate corrects them. Run 2 examines those rows and the rows that cite the changed files. The other rows keep their last confirmed (run N).

R-4 — Progress guard

The delegate SHALL halt when a verifier run makes no progress. No progress means that a breach from the previous run is still there, or that more rows fail than in the previous run.

  • WHEN run 3 fails a row on the same breach as run 2
  • THEN the delegate halts, also with fix attempts left.
  • WHEN run 3 fails one row on a new breach, and run 2 failed one row
  • THEN the delegate continues.

R-5 — Conclusions guard

The delegate SHALL halt immediately when the next correction would change a phase conclusion, a delegated decision or an ADR.

  • WHEN the only correction for a failed row changes a delegated decision
  • THEN the delegate halts before the correction, whatever the budget.

R-6 — Ceiling and fail-safe

The budget SHALL be at most 10. A fixes value that is not a whole number from 1 to 10 SHALL count as 1.

  • WHEN a file sets fixes: 12 or fixes: many
  • THEN the effective budget is 1.

R-7 — Log line

The delegate SHALL write one log line for each fix attempt: fix attempt <n> of <fixes>: run <N> failed rows <list>.

  • WHEN the delegate makes its second fix attempt with fixes: 3
  • THEN log.md gets fix attempt 2 of 3: run 2 failed rows ….

R-8 — After a stop

After a stop, the Architect's answer SHALL set the rows for the next verifier run, and whether the delegate may make more fix attempts. Without such an answer, one verifier run SHALL follow, and a failed row SHALL be a new stop.

  • WHEN the Architect replies "yes" to a stop that names two rows
  • THEN one verifier run examines the two rows. A failed row is a new stop.

R-9 — Stop condition 5

Stop condition 5 SHALL name three causes: a used-up budget, no progress, and a correction that changes a conclusion, a delegated decision or an ADR.

  • WHEN a reader looks for the cause of a stop at a gate test
  • THEN condition 5 names all three causes.

R-10 — Phase 05 accept

The Phase 05 accept step SHALL use the same budget and guards. When the delegate used all its fix attempts, or a verifier run makes no progress, the delegate SHALL reject the implementation (05b). A correction that changes a conclusion SHALL be a stop.

  • WHEN phases.implementation.fixes: 2 and the accept step fails twice with progress
  • THEN the delegate makes two fix attempts, then rejects the implementation and starts 05b.

R-11 — Template version 3

The template SHALL be version 3, with fixes: 5, its comment, its legend line and fixes: inherit on five phases. The Keys row SHALL say that the current version is 3. The README copy SHALL be equal to the template.

  • WHEN speccen writes a new project file
  • THEN the file has version: 3 and every fixes line, and the README shows the same block.

R-12 — Upgrade

The upgrade of a project file to version 3 SHALL add fixes: 5 and fixes: inherit on five phases and set version: 3. The value added SHALL be the value its absence means, so the upgrade keeps every effective setting. Both lists of absence values SHALL name 5.

  • WHEN speccen brings the version-2 project file of this repository to version 3
  • THEN the file gets fixes: 5, five fixes: inherit lines and version: 3. No value the Architect set changes.

R-13 — Locks

A project lock SHALL prevent a higher fixes in a bundle file or a local file, as for every other key.

  • WHEN the project file sets lock: true on code-analysis and a bundle file sets phases.code-analysis.fixes: 3
  • THEN the session ignores the bundle value. The session shows one message about the lock.

R-14 — Self-check line

The self-check line SHALL be Self-check: done — N corrections.

  • WHEN a gate test writes its self-check line
  • THEN the line shows "N corrections", and "fix" means only a gate-test fix attempt.

R-15 — Scope

The update SHALL touch only the governing skill, the Phase 05 skill and the README.

  • WHEN the update lands
  • THEN git diff --stat outside .speccen/ shows only those three files.
