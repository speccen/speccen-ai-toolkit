What the update builds

speccen gives each question, decision and item a label, for example DD-4, 01/8 or row 16. The labels make the decisions traceable. Today a stop round or a review round often shows the label alone. The Architect must then open other files to learn what the question is about.

This update adds one rule to the governing skill. Each item that speccen puts to the Architect has a subject in the form [INTERNAL-NUMBER | HUMAN UNDERSTANDABLE TEXT], for example [DD-4 | Does the fix budget also cover Phase 05's own fix rule?]. The number keeps the item traceable. The text tells the Architect what the item is. A label never stands alone.

Each place that puts items to the Architect points to the rule. The records in the bundle do not change: they are records, not questions.

The Architect added a second change during this run. A correction that only changes how a decision is recorded is not a stop. Examples: one question becomes two with the same answer, or a question moves to a later round. The delegate keeps the answer, writes what it repaired, and continues.

Source: the Architect's brief (issue #26), the Phase 01 analysis, the Phase 03 decisions and the scope addition.

Terms

  • Subject — the pair [number | text] that names one item.
  • Label — the number alone, for example DD-4.
  • Record — a table or log line in the bundle: the gate check, the delegated decisions, the interview tables, the Retrospective's findings, the fix-attempt log line.
  • Record repair — a correction that changes how a decision is recorded, not what it decides.

Requirements and acceptance scenarios

Requirement: R-1 — The rule, stated once

The governing skill SHALL state once, at the end of Structured questions, that anything put to the Architect reads on its own: every question, decision, checklist row or open item it mentions has a [INTERNAL-NUMBER | HUMAN UNDERSTANDABLE TEXT] subject, for every label kind including numbers a bundle invents; in a table the bar is escaped with a backslash.

Scenario: A label in a stop round

  • WHEN a stop round names DD-4
  • THEN it reads [DD-4 | Does the fix budget also cover Phase 05's own fix rule?], never DD-4 alone.

Scenario: A subject in a table

  • WHEN the subject sits in a table cell
  • THEN its bar is escaped and the table renders.

Source: brief §2, §2.1; 03/2, 03/10, 03/12 (DD-10, DD-18, DD-20); Phase 03 domain note

Requirement: R-2 — Records keep their form

The rule SHALL cover only what is put to the Architect; the gate-check, delegated-decision and interview tables, the Retrospective's delegation findings and the fix-attempt log line SHALL keep their form.

Scenario: Gate-check rows

  • WHEN a gate check is written
  • THEN its rows keep their numbers and form.

Scenario: Fix-attempt line

  • WHEN a fix attempt is logged
  • THEN the line is fix attempt <n> of <fixes>: run <N> failed rows <list>.

Source: brief §3, §5.2; 03/3, 03/7, 03/21 (DD-11, DD-15, DD-25)

The plan

Six implementation phases. The full plan is in phase.md.

  1. The rule. Add the Subjects paragraph to Structured questions. Why: every pointer names the rule, so the rule comes first. It goes at the end of the section because it governs the tool and the interview (brief §2.1; 03/2, 03/10).
  2. Governing pointers. Point the stop record, the stop line, the stops: proceed item, the resume summary and the end-of-run report to the rule. Add the sixth self-check item. Why: the governing skill writes these messages, and the self-check enforces the rule (brief §2.4 – §2.6; 03/4, 03/5, 03/17, 03/20).
  3. Interview. Change the round template, the review round and the closing summary. Why: the template is the shape of every interview, so one change reaches all of them (brief §2.2, §2.3; 03/9, 03/18).
  4. Phase 05 and reconcile. Give waived tests and contradictory decisions their subjects. Why: these two skills also put items to a person (03/19, 03/6).
  5. Stop condition 5. Narrow the trigger in each place that states it, and keep the README template copy identical. Why: the Architect added this change and applied it to this run (03/16, 03/24).
  6. README and verification. Name the form in the README. Run the text checks. Why: the README tells the Architect what a stop and a review look like (03/14); the checks prove each requirement.
